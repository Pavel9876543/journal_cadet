# Исправление архитектуры связей журнала

## Причина регрессии

В проекте одновременно существовало несколько независимых правил доступа.
Личный кабинет, фильтры, формы и API отдельно соединяли таблицы назначений,
служебные записи участия и сохранённые результаты. Поэтому одна страница могла
видеть `AssessmentResult`, а другая — считать, что ученику ничего не назначено.
Отдельные выборки также использовали текущие флаги `Student.is_active` и
`Teacher.is_active` вместо записей конкретного учебного года.

Проверка предоставленного дампа показала, что основные назначения в базе есть и
согласованы: проблема возникала именно в чтении и фильтрации, а не в отсутствии
учеников, преподавателей или результатов. Сам дамп в проект не включён.

## Новая модель

`journal/access_scope.py` является единым слоем чтения и проверки прав.

| Данные | Каноническая связь |
|---|---|
| Участие ученика в году | `StudentEnrollment` |
| Групповой предмет преподавателя | `GroupSubject` |
| Индивидуальный предмет преподавателя | `StudentSubject` |
| Ответственный за произведение | `AssessmentItem.responsible_teacher` |
| Ученик в группе произведений | `StudentAssessmentGroup` |

`Grade`, `SubjectResult` и `AssessmentResult` больше не создают доступ задним
числом. `TeacherEnrollment`, `TeacherSubject` и
`UserAcademicYearMembership` синхронизируются для истории, но не предоставляют
и не отбирают доступ.

## Исправленные сценарии

- администратор получает все назначенные предметы и группы произведений;
- преподаватель видит и изменяет только точные пары ученик/предмет и только
  произведения, где он назначен ответственным;
- оценка, созданная администратором, видна назначенному преподавателю, потому
  что автор оценки не является правилом доступа;
- независимые наборы учеников и предметов больше не образуют ложные
  перекрёстные комбинации;
- архивные назначения остаются доступными для просмотра;
- текущие профильные флаги не скрывают историю и не подменяют зачисление;
- формы, API и личные кабинеты используют одинаковые QuerySet-правила;
- активация учебного года формирует текущий статус преподавателя из реальных
  назначений, а не из служебной таблицы участия.

## Миграция 0038

Миграция:

1. синхронизирует предмет и учебный год произведения с его группой;
2. синхронизирует учебный год и зачисление назначения ученика;
3. объединяет устаревшие дубликаты `ученик + группа произведений`;
4. восстанавливает служебные записи преподавателей из настоящих назначений;
5. синхронизирует текущие карточки учеников и преподавателей с активным годом;
6. не создаёт назначений на основании сохранённых оценок или результатов.

## Проверка после установки

```bash
python manage.py migrate
python manage.py audit_journal_relations
python manage.py test
```

Для Docker development:

```bash
docker compose exec web python manage.py migrate
docker compose exec web python manage.py audit_journal_relations
docker compose exec web python manage.py test
```

До обновления рабочей базы рекомендуется сохранить `pg_dump`.
